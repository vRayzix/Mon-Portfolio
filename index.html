Gestion du Trafic Aérien — Django & MariaDB

Application web de gestion du trafic aérien (CRUD de 6 entités, logique métier, import CSV, fiches imprimables) déployée « comme en production » sur deux VM Debian (Nginx + Gunicorn + systemd).

AC13.01 · AC13.02 · AC13.04 · AC13.05 · AC13.06 — CE3.01 → CE3.05

Code source sur GitHub
Voir le portfolio complet de la SAÉ

1. Contexte du projet

En équipe de trois, nous devions développer une application web de gestion du trafic aérien : un gestionnaire administre des aéroports, des pistes, des compagnies, des types d'avions, des avions et des vols, avec un CRUD complet pour chaque entité. Le sujet imposait une logique métier (vérifier qu'une piste compatible est libre à l'arrivée — occupation de 10 minutes par avion, avec suggestion d'un créneau sinon), un import de vols par CSV et la génération de fiches de vols imprimables. L'application devait être déployée en production sur machine virtuelle avec Nginx et Gunicorn — le cœur de la compétence UE3.

MembrePérimètre
Moi (Lucas)Infrastructure VM, déploiement Nginx/Gunicorn/systemd, front-end (templates, CSS, tableau de bord), import CSV, fiches de vols, documentation technique.
AdilBack-end Django : modèles, formulaires, vues CRUD et logique des 10 minutes (suggestion de créneau).
AdelSchéma SQL (schema.sql), création et alimentation de la base (donnees.sql), tests de robustesse.

Outils communs : Git/GitHub (code), ClickUp (planning Gantt), VirtualBox (VM).

2. Mes tâches réalisées personnellement

2.1 Infrastructure & réseau (deux VM)
  • Deux VM Debian sous VirtualBox : une VM « BDD » (MariaDB seule) et une VM « Django » (Nginx + Gunicorn + application).
  • Passage en mode pont : chaque VM reçoit une IP du réseau de la salle via DHCP, rendant le site joignable depuis n'importe quel poste.
  • MariaDB configurée pour les connexions distantes (bind-address = 0.0.0.0, utilisateur django_user@'%').
2.2 Déploiement Nginx + Gunicorn + systemd
  • Gunicorn (WSGI) en remplacement du runserver de développement, Nginx en reverse proxy.
  • Blocs /static/ et /media/ dans Nginx, collectstatic côté Django (STATIC_ROOT).
  • Service systemd avec systemctl enable pour un redémarrage automatique après reboot.
  • Rédaction de DEPLOIEMENT.md — procédure complète et reproductible de A à Z.
2.3 Front-end & expérience utilisateur
  • Gabarit commun base.html (navigation + barre latérale) hérité par toutes les pages.
  • Pages de liste des 6 entités, formulaire générique réutilisé pour tous les CRUD, page de confirmation de suppression.
  • Tableau de bord à compteurs dynamiques interrogeant la base en temps réel.
  • CSS séparé (thème sombre à barre latérale), indépendant de Bootstrap.
2.4 Import CSV & fiches de vols
  • Module import_vols_csv : lecture UTF-8, correspondance par nom, collecte d'erreurs ligne par ligne sans interrompre l'import, mode d'emploi en préambule.
  • Page fiche_vols : filtrage par aéroport, date et sens (départs/arrivées) + feuille @media print pour une impression propre.
2.5 Gestion de version & coordination
  • Tenue du dépôt GitHub, résolution des conflits de fusion (notamment dans settings.py), synchronisation du code sur les VM.
  • Planification via diagramme de Gantt (ClickUp) et intégration des corrections du professeur (base SQL manuelle plutôt que migrations Django).

Analyse réflexive — difficultés & résolution

Le déploiement a été la partie la plus formatrice : les problèmes ne venaient pas du code applicatif mais de l'environnement. J'ai appris à diagnostiquer en couches plutôt qu'à essayer au hasard.

ProblèmeDiagnosticSolution
502 Bad GatewayGunicorn injoignable par Nginx.Diagnostic couche par couche : ss -tlnp → curl 127.0.0.1:8000 → logs Nginx.
ModuleNotFoundError: pymysqlGunicorn lancé hors du virtualenv.Toujours activer le venv avant de démarrer Gunicorn.
Conflit dans settings.pyMarqueurs de conflit Git non résolus cassant le parse Python.Résolution manuelle (ALLOWED_HOSTS, HOST de la base).
Gunicorn ne survit pas au rebootUnité systemd non enregistrée.systemctl enable gunicorn avec chemin absolu.

Ce que je retiens : un service web ne se résume pas à son code. Sa valeur tient aussi à sa capacité à être déployé, reproduit et maintenu — d'où l'importance de la documentation et d'une méthode de diagnostic ordonnée.

4. English summary

As part of SAÉ 2.03, our team of three built an air-traffic management web application using Django and MariaDB. The app provides full CRUD operations for six entities (airports, runways, airlines, aircraft types, aircraft and flights), enforces a runway-availability business rule (a runway stays busy for ten minutes after a landing, otherwise a later slot is suggested), supports bulk flight imports via CSV, and generates printable flight sheets.

My personal scope covered infrastructure setup (two Debian VMs in bridged networking — one for MariaDB, one for the Django app behind Gunicorn and Nginx), a systemd service for automatic restarts, the front-end (shared template, sidebar layout, dynamic dashboard), the CSV import module and the deployment documentation. The most valuable learning came from deployment troubleshooting: diagnosing a 502 error layer by layer taught me that a web service is more than its code — reproducibility, documentation and a structured diagnostic approach are equally critical skills.

Architecture Réseau Succursale — EVE-NG

Conception et déploiement sous EVE-NG d'un réseau d'entreprise complet (Cisco) : segmentation VLAN, routage inter-VLAN, DHCP relayé et VTP.

AC11.03 · AC11.04 · AC11.05 — CE1.01 · CE1.02 · CE1.03

Voir le détail de la SAÉ

Contexte

Simulation sous EVE-NG (équipements Cisco 2960 + 2800) d'une succursale d'entreprise connectée à un siège (sujet R1.02).

Mes tâches

  • Segmentation : 4 VLANs (Directeurs, Utilisateurs, Serveurs, Administration) isolés par politique de sécurité.
  • Inter-VLAN : Router-on-a-Stick (sous-interfaces 802.1Q sur le routeur).
  • Services : DHCP déployé sur le commutateur puis migré sur serveur Linux avec relai ip helper-address ; VTP serveur/client entre les deux commutateurs ; spanning-tree contre les boucles.

  • CE1.01 — choix d'une topologie Cisco et d'un adressage adaptés.
  • CE1.02 — segmentation VLAN comme mesure de sécurité.
  • CE1.03 — diagnostic rigoureux par ping/traceroute.

English summary

Using EVE-NG, I deployed a complete corporate branch network on Cisco devices: four security-segmented VLANs, inter-VLAN routing (router-on-a-stick), DHCP first on the switch then relayed to a Linux server via ip helper-address, and VTP between switches. I validated connectivity layer by layer with ping and traceroute.

Architecture réseau avancée sous GNS3 : routage dynamique RIPv2, load-balancing spanning-tree, services FTP/Apache, port-security et ACL.

AC11.03 · AC11.04 · AC11.05 — CE1.01 · CE1.02 · CE1.03

Voir le détail de la SAÉ

Infrastructure réseau multi-sites sous GNS3 avec services d'entreprise avancés (sujet RT11).

Security relied on port-security and layered ACLs on R2 and the border router.

UE2 · Embarqué SAÉ 2.02 · S2

Radio Internet ESP32 — MURA

Radio internet embarquée sur ESP32 (HUZZAH32) + codec VS1053 : streaming Wi-Fi, décodage MP3/AAC, écran OLED, contrôle MQTT et application Flutter Android.

AC11.01 · AC11.02 · AC12.03 · AC12.04 · AC13.03 — CE2.02 · CE2.03 · CE2.04

Voir le détail de la SAÉ

Contexte

Conception complète d'une radio internet autonome : matériel, firmware et application de contrôle.

Hardware

  • Adafruit HUZZAH32 (ESP32 — Wi-Fi + Bluetooth) ; codec audio VS1053 (décodage MP3/AAC matériel, SPI).
  • Écran OLED SSD1306 128×32 en I²C (SDA → GPIO23, SCL → GPIO22) ; haut-parleurs LS110 4 Ω 5 W × 2.
  • Boîtier bois custom, alimentation batterie 18650 Li-ion 2P (montage parallèle) sur port LiPo.

Firmware & application

  • Streaming Wi-Fi HTTP vers le VS1053 (35 000+ stations via Radio Browser API).
  • Correction logarithmique du volume f(x) = 50 + √(x/100) × 50 ; égaliseur 5 bandes (registres VS1053), 6 présets en EEPROM.
  • Contrôle complet via MQTT (pub/sub) ; affichage OLED (station, IP, état, volume).
  • Application Flutter Android : catalogue 35 000 stations, provider MQTT temps réel, favoris persistés (shared_preferences), thème Material 3.

Preuves — composantes essentielles (UE2)

  • CE2.02 — démarche scientifique : correction perceptive du volume, réglage de l'égaliseur.
  • CE2.03 — choix d'un codec matériel et d'une liaison MQTT adaptés.
  • CE2.04 — boîtier bois et batterie réutilisable (sobriété matérielle).

English summary

MURA is a self-contained internet radio built on an ESP32 (HUZZAH32) with a VS1053 hardware codec. It streams over Wi-Fi from 35,000+ stations, decodes MP3/AAC, shows status on an OLED display and is fully controllable over MQTT, including a 5-band equaliser and a logarithmic volume curve. A companion Flutter Android app provides real-time control and persisted favourites.
